## This is a single-vendor store, not the marketplace the reference schema implies
Correction to the reference-schema note: `database/backend-sport-accessorie.sql` is a multi-vendor marketplace dump (6amMart/GetIR-style — has `shops`, `shop_followers`, per-seller `withdrawal_methods`/`shipping_types`, etc.). This app is single-vendor. Use the dump for column/field naming ideas on generic tables, but skip or adapt anything modeling multiple sellers (seller_id, shop_id, per-vendor payouts) — there is one storefront, not a marketplace. `withdrawal_methods` (built 2026-08-20) leans marketplace-flavored; treat as vendor/supplier payout config for the single business, not per-seller payouts, if revisited.

## Users CRUD built (2026-08-22) — admin accounts + role assignment
Built alongside a concurrent session's Roles feature (Spatie roles/permissions, RoleController). Users CRUD: App\Http\Controllers\Backend\UserController (full index/create/store/edit/update/destroy, dedicated pages — User has 4+ real fields including password). App\Http\Requests\Backend\Store/UpdateUserRequest (password via Illuminate\Validation\Rules\Password, confirmed; nullable on update to keep current password). App\Actions\Users\{Create,Update,Delete}UserAction — sync roles via $user->syncRoles(), roles submitted/validated as integer IDs (Rule::exists('roles','id')) to match the Roles feature's permissions-as-IDs convention, not names. No new migration — reuses App\Models\User (already has Spatie HasRoles trait) and the existing permission_tables migration. Route: users (resource, except show).

Gotcha: User model has #[Fillable(['name','email','password'])] — email_verified_at is NOT fillable, so User::create([...,'email_verified_at'=>now()]) silently drops it (no strict-mode guard enabled in AppServiceProvider). CreateUserAction sets it via ->forceFill(['email_verified_at'=>now()])->save() after create(), otherwise admin-created users can't pass the `verified` middleware and get locked out with no verification email flow to unblock them.

UserController::destroy guards against an admin deleting their own account ($user->is($request->user())) — controller-level check, not an Action concern since it depends on the authenticated request context. Don't rebuild — extend the existing files instead.

## Roles CRUD built (2026-08-22) — rides on spatie/laravel-permission, no new table
Built role management directly on Spatie's own `Spatie\Permission\Models\Role`/`Permission` models — no new App\Models\Role or migration, the tables already exist (permission_tables migration, User has HasRoles). App\Http\Controllers\Backend\RoleController (index/store/update/destroy only — modal CRUD per [[controllers]], role has just 1 real field `name` + a permissions relation). App\Actions\Roles\{Create,Update,Delete}RoleAction: Create/Update call `$role->syncPermissions($data['permissions'] ?? [])` inside DB::transaction (update always replaces the full permission set, doesn't merge). App\Http\Requests\Backend\{Store,Update}RoleRequest validate `permissions.*` as integer permission IDs (`Rule::exists('permissions','id')`), not names — keep this shape consistent with any future User role-assignment UI. `name` unique per `guard_name = 'web'` (single-guard app). The `admin` role (seeded in RolePermissionSeeder) is protected from deletion — guarded in the controller's destroy() with a plain name check before calling the action, not in the Action itself. Route: `roles` (resource, only index/store/update/destroy). Sidebar: new "Administrator" nav group in AppSidebar.vue (was empty before this). Currently 0 permissions exist in the DB — the UI handles an empty permission catalog gracefully (shows "No permissions defined yet" instead of an empty checkbox grid); permissions themselves are still meant to be seeded in RolePermissionSeeder per [[http]], not invented ad hoc here. Don't rebuild — extend the existing files instead.
