# Business Settings

## Business settings extended (2026-08-29): hours, days, pagination, invoice, timezone, location, login limit, guest checkout
Added 9 more key-value settings to the existing store-only DEFAULTS const in BusinessSettingService: working_hours_open/working_hours_close ('H:i' strings), working_days (CSV of mon/tue/.../sun, submitted as `working_days[]` checkboxes and imploded to CSV in the controller before save — the FormRequest validates it as an array via `working_days.*` then the controller does the CSV conversion, don't pass the array straight to the service), time_zone (validated with Laravel's built-in `timezone` rule; controller passes `DateTimeZone::listIdentifiers()` as an extra `timezones` Inertia prop for the Select options), detail_location (free-text landmark/directions, not lat/lng — no map integration exists in this app), pagination_limit, invoice_prefix, max_login_attempts, guest_checkout (bool like tax_included_in_price/maintenance_mode). Like every other setting here, these are storage-only — nothing in the app actually enforces pagination_limit, max_login_attempts, or guest_checkout yet (same as maintenance_mode/tax_included_in_price, which also aren't wired to real gating). Frontend Edit.vue gained two new Cards ("Hours & availability", "Catalog display") and extended "Contact & location", "Commerce", "System".

Pre-existing unrelated bug hit while testing this: `test_users_without_the_edit_permission_cannot_update_business_settings` was already failing before this change (UserFactory assigns 'admin' role by default, and AppServiceProvider's `Gate::before` bypasses ALL permission checks for admins, so a plain `User::factory()->create()` can never get 403 from a permission-gated route — the test needs `->syncRoles([])` like `actingAsUserWithoutPermissions()` does elsewhere in the same file, but wasn't given it). Once the new required fields (time_zone/pagination_limit/max_login_attempts) made validation actually fail for that test's minimal payload, PHPUnit's own failure-message enrichment (`TestResponseAssert::injectResponseContext`) crashed with "Call to a member function all() on array" trying `session('errors')->all()` — Inertia flashes validation errors as a plain array, not a MessageBag/ViewErrorBag, so that enrichment path is fundamentally incompatible with Inertia validation redirects app-wide, not specific to business settings. Left both bugs alone (out of scope), but don't be surprised by them — not caused by whatever you're touching.
