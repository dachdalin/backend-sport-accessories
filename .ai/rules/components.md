# Components

## New-order notifications (web + Telegram) built (2026-08-27)
Built admin notifications for new orders, fired from both order-creation paths (backend App\Actions\Orders\CreateOrderAction and API App\Actions\Orders\ProcessOrderAction — NOT an Order model `created` event, because that would fire for every Order::factory() call across the whole test suite): each Action calls `OrderPlaced::dispatch($order)` at the end of its DB::transaction() closure. App\Events\OrderPlaced implements `Illuminate\Contracts\Events\ShouldDispatchAfterCommit` (not `Illuminate\Queue\ShouldDispatchAfterCommit` — wrong namespace, doesn't exist) so listeners only run after the transaction actually commits.

Gotcha: `ShouldDispatchAfterCommit` callbacks never fire under RefreshDatabase tests, because the test's wrapping transaction is rolled back, not committed (see Illuminate\Database\DatabaseTransactionsManager::commit(), which only executes callbacks at transaction level 0). So event/notification side effects can't be asserted end-to-end through the HTTP layer in tests — test each layer in isolation instead: `Event::fake()` + `Event::assertDispatched(OrderPlaced::class)` at the Action/controller level; instantiate `App\Listeners\SendNewOrderNotifications` directly and call `->handle(new OrderPlaced($order))` with `Notification::fake()` to test the listener; unit-test `App\Notifications\NewOrderPlaced::toDatabase()/toTelegram()` directly; `Http::fake()` for `App\Notifications\Channels\TelegramChannel`. See tests/Feature/NewOrderNotificationTest.php, TelegramChannelTest.php.

SendNewOrderNotifications (ShouldQueue) sends `NewOrderPlaced` (also ShouldQueue) to every `App\Models\User` via the `database` channel (web bell), plus `Notification::route('telegram', config('services.telegram.chat_id'))->notify(...)` when `services.telegram.bot_token`/`chat_id` are both configured (single store-wide chat via .env, not per-admin — matches this app's single-vendor/single-admin-team setup). `NewOrderPlaced::via()` returns `[TelegramChannel::class]` for `AnonymousNotifiable` (on-demand) and `['database']` otherwise. TelegramChannel is a plain custom channel class (no `Notification::extend()` registration needed — Laravel's ChannelManager resolves an unrecognized driver name that is a real class via the container) that POSTs to `https://api.telegram.org/bot{token}/sendMessage` with timeout/retry, no-ops silently if token/chat_id missing.

Web side: App\Services\NotificationService::summary(User $user) now takes the acting admin and merges their real unread `database` notifications (id/type/title/subtitle/timestamp/href from the notification's `data` array) with the still-computed pendingReviews/openTickets/unreadContacts sections (those three are unchanged, NOT converted to persisted notifications — only orders were in scope). `total` count now sums `$user->unreadNotifications()->count()` + the three live counts. HandleInertiaRequests passes `$request->user()` into `summary()`. Mark-as-read: `App\Http\Controllers\Backend\NotificationController@read` (single, route-model-bound `DatabaseNotification`, ownership checked manually since DatabaseNotification has no notifiable_is() helper) and `@readAll`, routes `notifications.read`/`notifications.read-all` in routes/web.php inside the `auth` group. NotificationBell.vue shows a per-item dismiss "×" (only when `item.id` is present, i.e. a real notification) and a header "Mark all as read" button (shown when any item has an id), both via `router.post(...)` + wayfinder-generated `NotificationController.read/readAll` actions (not `<Form>`, following the ManagePasskeys.vue imperative-action pattern since these aren't real forms).

`notifications` table is the stock `php artisan notifications:table` migration (uuid PK) — standard Laravel, don't hand-roll. `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` added to config/services.php + .env/.env.example (both empty by default; feature no-ops until an admin fills them in). Don't rebuild — extend these files instead.
